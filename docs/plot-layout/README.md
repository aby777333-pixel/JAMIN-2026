# Plot layout renderers

Portable implementations of the sanctioned-layout plan, so the same geometry can
be drawn wherever it is needed. All of them consume the **same** data contract,
generated from the DTCP approval drawing by
`scripts/extract-dtcp-layout.py`.

| Target | File | Status |
| --- | --- | --- |
| SVG (primary, self-contained) | `web/edappadi-layout.svg` | generated by `scripts/render-layout-svg.py` |
| Responsive HTML/CSS + JS | `web/layout.html`, `web/layout.js` | shipped — the public plot selector |
| React Native (in-app) | `src/features/layouts/PlotMap.tsx` | shipped — uses `react-native-svg` |
| Admin console | `web/admin.html` → Plot layouts tab | shipped |
| HTML5 Canvas | `canvas-renderer.js` | reference |
| Flutter `CustomPainter` | `plot_layout_painter.dart` | reference |

`canvas-renderer.js` and `plot_layout_painter.dart` are **reference
implementations**, deliberately not wired into this repo: JAMIN is an Expo /
React Native app, so there is no Flutter target here and the shipped web viewer
uses SVG (it stays crisp at any zoom, which a canvas bitmap does not). They exist
so the layout can be dropped into a Flutter app or a canvas/WebGL surface later
without re-deriving the geometry.

## The data contract

Every renderer reads the same object:

```jsonc
{
  "viewBox": [30, 100, 300, 540],       // x, y, w, h in drawing user space
  "boundary": [[150.21, 133.03], ...],  // sanctioned site boundary, open ring
  "osr": {
    "rect":    [206.06, 296.11, 306.59, 363.14], // as drawn (overhangs the site)
    "polygon": [[206.06, 296.11], ...],          // the part inside the site — draw this
    "areaSqm": 1342.0,
    "label":   "O.S.R."
  },
  "existingRoad": { "quad": [[44.09, 588.77], ...], "label": "...", "widthM": 12.0 },
  "roads":      [{ "label": "9.00 m ROAD", "widthM": 9.0, "band": [x0,y0,x1,y1], "rotate": -84 }],
  "dimensions": [
    // `measures` = the boundary vertices this callout spans. The callout LINE is
    // drawn offset from the site and runs 3-4% short, so never measure with it.
    { "label": "72.40 m", "from": [x,y], "to": [x,y], "measures": [0, 1] }
  ],
  "metresPerUnit": 0.547243,   // scale-bar only — never for areas or sizes
  "plots": [
    { "number": 1, "block": "A", "rect": [x0,y0,x1,y1],
      "widthM": 12.2, "depthM": 18.3, "areaSqm": 223.26, "facing": "south" }
  ]
}
```

### Rules every renderer must follow

1. **Coordinates are the drawing's own user space** (points, y-down — same as
   SVG, so no axis flip). They exist to position things on screen and for
   nothing else.
2. **Never compute an area or a size from the coordinates.** The drawn
   rectangles are set out to fill each row band and read ~1–2% off the quoted
   metres. Sizes and areas always come from `widthM` / `depthM` / `areaSqm`,
   which are transcribed from the sanctioned plot schedule.
3. **Draw the boundary polygon as the road fill**, then the OSR, then the plots
   on top. What shows through is exactly the road area. Do not clip a rectangle
   to the boundary — not every consumer honours clip paths.
4. **Use `osr.polygon`, not `osr.rect`.** The rectangle as drawn runs past the
   site edge.
4b. **Use `plotShapes[number]`, not `plot.rect`, to draw a plot.** The approval
   sheet clips its plot rectangles to the site boundary, and eight plots
   (5, 10, 15, 18, 20, 22, 24, 26) run past the edge by up to 5 m — the drawing
   shows the boundary line as their edge. Draw `poly` when `clipped` is true and
   the rounded rectangle otherwise, and anchor labels and state badges on `at`
   (the polygon centroid), never on the rectangle centre. `rect` remains the
   sanctioned set-out and is what the plot schedule refers to.
5. `facing` and `is_corner` are read off the plan and are **not** stated on the
   DTCP sheet. Never present them as approval facts.
6. **`metresPerUnit` drives the scale bar and nothing else.** It is a
   least-squares fit of the three overall dimensions against the boundary edges
   they annotate. The sheet is not perfectly uniform — those edges individually
   imply 0.5395, 0.5492 and 0.5475 m/unit — so the fit is the honest single
   number, good to ~1.5%. Any figure a buyer sees must come from the schedule.
7. **Annotate each plot with its number and rounded area.** Round for the plan
   (`223 m²`); the exact schedule value belongs in the detail sheet. Specify
   `Inter, Helvetica, Arial, sans-serif` — a serif fallback is wide enough to
   overflow the plot box.

## Plot states

| State | Fill | Stroke | Number | Mark |
| --- | --- | --- | --- | --- |
| available | white | green `#1E9E5A` | green | — |
| selected | blue `#2F6BFF` | `#1B4FD8` | white | glow + lift |
| reserved | amber `#E6A10D` | `#B4790A` | white | clock + `HELD` |
| booked | red `#FD0001` | `#C70000` | white | lock + `BOOKED` |
| sold | grey `#4A4A4A` | `#2E2E2E` | white | `SOLD` |
| blocked | `#E6E7E2` | `#74746E` dashed | muted | — |

## Regenerating

```bash
python scripts/extract-dtcp-layout.py "path/to/DTCP Layout Approval Drawing.pdf"
python scripts/render-layout-svg.py
```

The first writes `src/features/layouts/data/edappadi.ts` and
`web/layout-data.js`; the second writes `web/edappadi-layout.svg`.
`src/features/layouts/__tests__/geometry.test.ts` then re-checks the output
against the plot schedule, so a bad extraction fails the build rather than
shipping a plan that no longer matches the approval.
